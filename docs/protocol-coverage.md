**Diagnostic route:** `GET /v1/operations` (any valid credential, no body, no query string) returns the bounded operation journal, newest first, at most 256 records: the caller's own operations plus the Deck's own display records. `ApiRoute.OPERATION_LIST` carries it (exact path, GET only; a query string, a body or a `POST` is rejected before anything is sent) and `ProtocolCodec` decodes it through `HostJournalDecoder`, which rebuilds every record from an allowlist: a list that is absent, not an array or over 256 records is "no journal" (`null`), a record whose `id`, `kind` or `state` is not a safe token (`^[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}$`) is dropped, strings are truncated and stripped of control characters, and `target` is kept only as a bounded map (at most 8 keys: scalars, string lists of at most 16, or one level of scalars). The generated `OperationListContractTest` cases prove each fixture decodes, including the `401` envelope; `HostJournalTest` pins the values and the degraded shapes. The records say what the host did and read back; none of them, a completed one included, shows that a picture is visible. The older body fixture `fixtures/operations-list.json` (the 0.5.18 list shape) stays claimed and is still decoded entry by entry by `ProtocolValidationTest.hostOperationListFixtureEntriesParseWithTheOperationDecoder`. The Android client reads it through `PinnedHostJournalGateway` and `HostJournalLoader` for the read-only Host journal section of Connection details: once when that screen opens and again on an explicit Refresh (reads spaced at least 5 s apart, one read per pairing, a request for another pairing replaces the older one), never from the 2-second status poll and never on a timer. The route needs only a valid credential, so the gateway checks no scope; a `404 not_found` from a host without the route, any other rejection, a transport or decode problem, or no network all mean "not available" and are silent. The records are held in memory only (`HostJournalViewModel`), tied to the pairing, cleared when the pairing changes, and never persisted or journaled. They reach a file only through the redacted diagnostic report of an explicit export, which copies named facts and never a record (see the cross-client vector paragraph); `DiagnosticExporterTest` pins that the persisted models have no field for them and that no sentinel of a seeded journal reaches the export. Wording comes from an embedded table that `HostJournalPresentationTest` checks against `operation-vocabulary.json`; an unknown code is shown as sanitised text rather than hidden.

**Cross-client vector:** `fixtures/diagnostic-report.json` is not a response. It is the shared vector for the redacted diagnostic report each client's explicit export may carry (`README.md`, "Diagnostic report"): eight cases give the four response bodies the report is built from (status, display outputs, DRM link facts, operation journal; each a contract-fixture path, an inline body, or `null` for "not read") and the exact `report` every client must rebuild. It adds no route and no request. `DiagnosticReportVectorTest` consumes it: each body is decoded with the app's own decoder, the decoded readings go through `DiagnosticReport`, and the compact JSON is compared byte for byte, so key order counts. The seven strict cases use only wire-schema-valid bodies, so the test asserts that the app's decoders accept every body of every one of them (no refusal, no output, connector or record dropped) and that each rebuilds exactly; there is no exception list and no decoder bound was changed for the report. The report is composed from the retained response body for the status and the display outputs (the decoded `HostSelfCheck` turns the plugin version `unknown` into null and `DisplayOutputSummary` keeps no `description`, both of which the report names) and from the decoded link facts and journal. `hostile-shape` (not strict) is the one case a decoder refuses (its status body has no `steam_bridge`, its display inventory has more than eight outputs, so both sections are null in the app), and it is checked to leak nothing and to be, per section, the reference, null, the reference with whole records dropped by a decoder (its link section: no connector of its fourteen is a conforming one), or the reference with a record's `target` cut to the first eight keys that `HostJournalDecoder` keeps (its journal section: every record has a nine-key target and loses `action`).

**Consumed defensively:** `self_check` is optional and is never allowed to fail a status read. `ProtocolCodec` decodes it through `HostSelfCheckDecoder`, which returns `null` for an absent, non-object or unusable block, drops a malformed or oversize section or field to `null`, and ignores unknown keys, so a host that predates the block, or one that extends it, still decodes. The generated cases above prove each status fixture decodes; `HostSelfCheckTest` pins the block's contents for the three new cases and the degraded shapes. The block is live status data only: it is not persisted or journaled, and an explicit export carries only its named facts through the redacted diagnostic report (never the listener address or the pin; `DiagnosticExporterTest.hostSelfCheckAddressAndPinAreNeverExportedWhileItsNamedFactsAre`). The shared strict JSON parser still applies to the whole response, block included (no duplicate keys, 4096 code points per string, depth and node caps, 256 KiB); the host schema keeps the block far inside those limits, so only a non-conforming host could trip them.

**Advisory route:** `GET /v1/drm` (`status.read`, no body, no query string) returns the kernel's per-connector facts so a client can warn, never block, before a display preview. `ApiRoute.DRM` carries it and `ProtocolCodec` decodes it through `LinkFactsDecoder`, which returns "no facts" (`null`) for an absent, non-object, mistyped or oversize block, drops a malformed connector, and ignores unknown keys. The generated `DrmContractTest` cases prove each fixture decodes, including the `401` envelope; `LinkFactsTest` pins the values and the degraded shapes. The list is resolutions only (no refresh rates) and the host does the connector-to-output join, so a client never matches by name. The Android client reads it through `PinnedLinkFactsGateway` and `LinkFactsLoader`: once when the Display screen opens and again when the output topology changes (spaced at least 5 s apart), never from the 2-second status poll, because the host rate-limits each client to 120 requests a minute and the poll already spends about 90. A `404 not_found` from a host without the route, or any other failure, means "no facts" and is silent. The facts are live and in memory only: not persisted or journaled, and an explicit export carries only their named fields through the redacted diagnostic report.

## Facts the fixtures established that differ from a reading of the source

- The host authenticates before it dispatches. An unknown `/v1/` path without a credential is `401 unauthorized`; with one it is `404 not_found`. A query string is rejected as `400 invalid_request` by the server before routing, not `404`.
- Pairing outcomes other than pending or delivery are errors, not `200` states: rejected and cancelled are `409`, expired is `410 pairing_expired`, and polling after delivery is `404 pairing_not_found` (`410 pairing_consumed` only if the host reloads between approval and poll).
- Every authenticated route and `/v1/pair/cancel` can return `429 rate_limited` with `Retry-After: 2`; `/v1/pair/request` also has `429 pairing_queue_full`.
- Every journaled mutation, including revoke-self, can return `409 request_id_conflict` for a reused request ID with a changed body; an identical replay returns `202` with the original operation.
- `POST /v1/display/order` and `/automatic` never return `503`; their failures are `400 invalid_request` and `409` stale/ambiguous/unsupported/update-failed. `POST /v1/power` does return `503 bridge_unavailable`.
- The error envelope is `{"error": "<code>", "message": "<text>"}`.

## Unreachable or not captured through the real handler

- `409 pairing_not_approved`: every stored pairing state is handled before that branch.
- `403` on `GET /v1/status`: every grant includes `status.read`. `403 forbidden` is captured on power, preview, and advanced pairing scope instead.
- `400 owner_confirmation_required` on save-current and `400 invalid_display_target` on set order: request validation rejects the same inputs first as `400 invalid_request`, which is captured.
- The "already revoked" message on revoke-self: a revoked credential fails generic authentication (`401`).
- `PUT`/`DELETE`: the standard-library server answers with a `501` HTML page, not JSON. `OPTIONS` (`405`) is captured. `413` body-too-large is not captured.

## Known host defect, pinned as observed

`GET /v1/power` with a valid `power.control` credential returns `500 internal_error` because the handler reads `action` from an empty body (`unsupported/get-on-power-route-authenticated.json`). The Android client never sends it. A host fix will change this fixture and require a deliberate pin update.
