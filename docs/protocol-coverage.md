**Contract pin:** Decky commit `40c97ac194b79424813c2aa840a78e545183a15d` on `main` (the merge of `protocol/android-contract-fixtures`), protocol tree `e5463866c87943c2602ae938fa428e0224f3b7c6` (see `protocol/SOURCE.json`). Host runtime behavior is `v0.5.18` (`50d71b7`); the contract-fixture merge does not change `host/backend`. Moving from the earlier pin (`804ebf1`, host `v0.5.16`) changed only `README.md`, `schema.json` (adds the `operations` array) and the new `fixtures/operations-list.json`; every contract fixture was byte-identical, so the hardened pairing deadlines and session checks in 0.5.17–0.5.18 did not alter any pinned response.

**Not consumed:** `GET /v1/operations` (the bounded operation list, added in 0.5.18) is pinned only as `fixtures/operations-list.json`, decoded by `ProtocolValidationTest.hostOperationListFixtureEntriesParseWithTheOperationDecoder`. The Android client never calls it: it reconciles through its own journal and `GET /v1/operations/{id}`, and `ApiRoute.match` rejects the list path. The host has no generated contract cases for the list route yet.

**How the fixtures were made:** `tests/contract_fixtures.py` in the Decky repository sends raw HTTP through the production `server._Handler` into `HostService.handle_http`, with the fakes from `tests/test_host.py`, a fixed clock, and deterministic identifiers. Each case asserts its expected status and error code while generating, and `tests/test_contract_fixtures.py` fails if a checked-in fixture drifts from what the host produces. Placeholders and normalised fields are documented in `protocol/README.md`. Nothing here was written by hand.

**What this table is:** one row per HTTP contract fixture, generated by `scripts/generate-protocol-coverage.py` from `protocol/fixtures/contract/index.json`. `scripts/verify-protocol-coverage.py` checks that every pinned route has a row, every contract fixture is hash-pinned and claimed by exactly the status it records, and every row names a Kotlin test method that exists in `core/src/test/kotlin`. The standalone host QR payload fixture at `fixtures/pairing-payload.json` is hash-pinned and parsed by `PairingModelsTest.hostBundledQrPayloadFixtureParsesWithTheAndroidClientValidator`.

## Facts the fixtures established that differ from a reading of the source

- The host authenticates before it dispatches. An unknown `/v1/` path without a credential is `401 unauthorized`; with one it is `404 not_found`. A query string is rejected as `400 invalid_request` by the server before routing, not `404`.
- Pairing outcomes other than pending or delivery are errors, not `200` states: rejected and cancelled are `409`, expired is `410 pairing_expired`, and polling after delivery is `404 pairing_not_found` (`410 pairing_consumed` only if the host reloads between approval and poll).
- Every authenticated route and `/v1/pair/cancel` can return `429 rate_limited` with `Retry-After: 2`; `/v1/pair/request` also has `429 pairing_queue_full`.
- Every journaled mutation, including revoke-self, can return `409 request_id_conflict` for a reused request ID with a changed body; an identical replay returns `202` with the original operation.
- `POST /v1/display/order` and `/automatic` never return `503`; their failures are `400 invalid_request` and `409` stale/ambiguous/unsupported/update-failed. `POST /v1/power` does return `503 bridge_unavailable`.
- The error envelope is `{"error": "<code>", "message": "<text>"}`.

## Unreachable or not captured through the real handler

- `409 pairing_not_approved`: every stored pairing state is handled before that branch.
- `403` on `GET /v1/status`: every grant includes `status.read`. `403 forbidden` is captured on power, preview, and advanced pairing scope instead.
- `400 owner_confirmation_required` on save-current and `400 invalid_display_target` on set order: request validation rejects the same inputs first as `400 invalid_request`, which is captured.
- The "already revoked" message on revoke-self: a revoked credential fails generic authentication (`401`).
- `PUT`/`DELETE`: the standard-library server answers with a `501` HTML page, not JSON. `OPTIONS` (`405`) is captured. `413` body-too-large is not captured.

## Known host defect, pinned as observed

`GET /v1/power` with a valid `power.control` credential returns `500 internal_error` because the handler reads `action` from an empty body (`unsupported/get-on-power-route-authenticated.json`). The Android client never sends it. A host fix will change this fixture and require a deliberate pin update.
