## Release policy and decisions

Checked 2026-09-28: [Google Play's target API requirements](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en) require new mobile apps and updates submitted from 2026-08-31 to target API 36 or higher. The baseline flavor meets that *target API requirement only*. The Play rule does not determine the project's release channel, signing ownership, or readiness. The target-37 flavor remains a separate permission-test configuration pending its full matrix.

Release channel and signing-key owner have not yet been recorded. No release signing configuration or checksum for a signed artifact exists. The project version is still `0.0.1`; it should be set deliberately before a release candidate is signed.

## Confirmed recovery-profile count mismatch

The tester supplied the precise Android 16 error: `/v1/display/outputs: PROTOCOL (Too many recovery profiles)`. Decky appends a new verified profile for each successful save/confirmation and does not cap the count at eight. Android's response parser capped the host list at eight, so a ninth profile hid every monitor and mode. Android now parses every profile within the existing 256 KiB response and bounded JSON limits, and its encrypted offline cache retains the last eight host entries. The live Display screen and fresh restore flow receive the full list. No Decky change is needed for this mismatch.

A 12-profile protocol regression confirms the outputs and full profile list decode; a repository regression confirms the last eight profiles remain durable. `:core:test :app:assembleBaselineDebug :app:assembleBaselineRelease` passed. ## Phase 10 display-order editing

The shared plan (`12-remote-monitor-order-control.md`) is still `planned-after-local-validation`; this work follows the pinned Decky host (`_display_order_target`, `gamescope.apply_order`) and the Omarchy client (`8130004`) and has **not** been run against a host with two physical monitors. Contract fixtures (`display-order-get|set|automatic`) all pass in JVM tests; live evidence is outstanding.

- **Draft model** (`DisplayOrderDraft`): editable rows are connected outputs only, saved priority first then inventory order. Move up/down is bounded. A background read never reorders a dirty draft; a changed generation, connected set, or connector marks it stale, and only Refresh accepts the new reading. A saved order holds the draft steady until the host reports it back. The draft survives tab switches and rotation.
- **Dispatch** (`DisplayDispatcher.saveOrder`, `saveOrderAndRestart`, `resetOrder`): fresh status, `display.control`, an available/unambiguous reading, matching generation, and keys that exactly equal the connected set. Refuses during an active preview and while any operation is unresolved, so an unknown restart is never replayed (reconcile with Check result). Restart additionally needs a captured `OrderRestartConfirmation` bound to the pairing, keys, and generation, and `restart_available`. Requests carry only host-issued keys, the generation, and the restart flag.
- **UI**: numbered priority rows with Move up/down, Save for next session, Save and restart Gaming Mode (confirmation, Cancel focused first, names the remote target and warns that games, the Steam UI and the stream close), Use automatic order, and Refresh order. No optimistic "active screen" claim.
- **Outcomes**: 409 `stale_display_inventory`/`stale_display_target` map to the stale-target reason, `ambiguous_display_identity`, `gamescope_output_unsupported` and `gamescope_output_update_failed` have typed reasons, and a failed operation with outcome `gamescope_output_configured_restart_failed` is recorded as `order_saved_restart_failed` so the UI says the order remains saved. The Latest display operation card compares the host's saved order with the request; it never claims the restart happened. The output-key limit is 16 (was 8, below the host and schema).
- **Still open for Phase 10**: end-to-end run against a real two-monitor host (save, manual session transition readback, save and restart, disconnect during restart, saved-order fallback with disconnected preferred outputs), old-host/new-client and offline-host behaviour on a device, duplicate-tap handling under the emulator, and TalkBack/200 % text review of the new rows. ## Kept preview left the journal unresolved; Display screen tabs

The tester reported that after Keep and save the top of Display showed "Result not confirmed", the Preview button disappeared, and display order stayed disabled with "Waiting for this preview to be kept or reverted", although Decky and SteamOS had applied the resolution.

**Cause.** The pinned host clears its live preview on a confirmed Keep or a completed preview revert, but leaves the original `display.preview` operation in `observed_return` (`_display_confirm`, `_run_restore_operation`). The Android journal therefore kept that preview entry unresolved forever. Every conflict check, the preview projection, the Preview button, and the display-order gate treat an unresolved entry as a blocker, so the screen was stuck until the entry was archived.

**Fix (Android only, no host change required).** A `display.confirm` for that preview ID that the host reports `succeeded`, or a preview-source `display.restore` the host reports `succeeded`, closes older unresolved preview entries of the same credential (`withSupersededPreviewsSettled`, applied on dispatch, on operation reconciliation, and at startup so an entry already stuck on a device is repaired). A different preview ID, a different credential, or an unfinished restore never closes it. A Keep already confirmed also hides the Keep button while the host's next read still shows the preview. Regression tests fail without the change. A preview that simply times out is still not inferred to be restored; it remains "not confirmed" until the operation is checked.

**Display screen.** Tabs are now Resolution, Saved, and Display order. Preview sits directly under the selected mode row, and Restore under the selected saved row, so neither is separated from its choice by a long list. Saved holds the deduplicated recovery modes (with output names) and Save current display. No new live evidence: the API 36 suite passes (47 tests, one LAN-matrix skip) but does not drive a Keep with a real host.

## Timed-out preview reverts; pairing-gate test made load-independent

A preview that runs out of time is restored by the host, so there is nothing left to keep. The host records this on the preview operation (`restore_state: "succeeded"`, `restored: true`, state left `observed_return`); Android now parses those two fields (`OperationSummary.hostRestored`) and finishes the preview entry when a lookup reports a verified restore. When the host's preview disappears while its operation is still open, the paired session asks the host for that operation itself, every four seconds and at most six times per entry, read-only, so the banner clears without a tap. An unknown, failed, or unverified restore stays "Result not confirmed" for the manual Check result. Restore facts on any other operation kind never finish it. No Decky change is needed; the host already exposes these fields.

`Phase02PairingGateTest.noncePairingShowsTheHostDerivedCodeAndStoresTheReturnedCredential` failed when the emulator was busy: the fake host ran scrypt before replying, so a loaded emulator missed the client's transport deadline (initial request came back `RequestUnconfirmed`, or the approval poll was never recorded). The fake host now derives the comparison code lazily after the exchange. The test passed on an API 36 emulator with 16 CPU-burning processes running on the development machine.

JVM totals: 363 core and 50 app tests, no failures. The API 36 baseline suite passed before this change (47 tests, one LAN-matrix skip); only the pairing-gate class was re-run after it.
