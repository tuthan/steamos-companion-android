## Implemented

- Phase 08: a network-bound Wake sender emits the standard 102-byte packet to the selected Wi-Fi/Ethernet path's directed and limited IPv4 broadcasts. It reports missing target/network, permission/send failure, and partial transmission separately. A foreground Wake attempt records packet transmission, a later authenticated host response, and Steam readiness as separate facts, with a 30-second no-response threshold and no automatic resend.
- Phase 08: Wake now checks the mandatory local-network grant before creating its UDP socket and again before each broadcast. A grant lost after the first packet is reported as a partial send without a second packet.
- Phase 08: the paired foreground session now accepts the result of one explicit Wake packet, requests a fresh authenticated status cycle, observes response and Steam readiness through the shared poller, and ticks the 30-second no-response state while the session is visible. Closing the Wake observation or stopping the paired session cancels its local countdown; reopening cannot send or resume a packet automatically. The Wake screen is wired; live packet capture remains pending.
- Phases 08–09: every successful foreground status poll now carries an ephemeral source identity bound to the selected host, endpoint, pin, pairing time, and bearer digest. Power, Sunshine, display recovery, and Wake observation reject a read from an older credential even if the host and client IDs are unchanged. The bearer itself is not copied into the UI observation state.
- Phase 08: the power and Sunshine dispatcher checks the exact saved pairing, granted `power.control` scope, fresh authenticated status, current capability, preview state, and unresolved operations immediately before journal dispatch. Power requires a confirmation bound to the target and exact verb. Sunshine also requires an observed stopped process. A journal result does not claim a physical power transition.
- Phase 08: Sunshine preflight now returns distinct typed reasons for monitoring off, owner provider unavailable, unknown process state, and a running/restarting process. The pinned status fixtures drive those distinctions. A stopped-state request rejected because Sunshine became running remains a failed journal operation while a later running observation remains a separate fact; no automatic restart retry follows.
- Phase 08: Sunshine preflight now also classifies the observed process state after capability validation. A contradictory host read that advertises restart capability while reporting disabled, unavailable, unknown, or an unrecognized Sunshine state cannot send a restart and retains the matching guidance.
- Phase 08: a power confirmation now captures the exact pairing fingerprint shown with the verb, including pin, pairing time, and bearer digest without retaining the bearer. A sheet opened before a same-host credential refresh cannot authorize the new pairing even if the endpoint and public IDs are unchanged.
- Phase 08: a pure control-card projection now keeps the power/Sunshine journal phase separate from a fresh authenticated observation. It distinguishes connection loss, host reachability, changed boot ID, and Sunshine running/stopped/unavailable. Unresolved migrated entries remain visible with unproven pairing provenance, while observations from a stale or different credential are not attributed to them.
- Phase 09: the display parser retains typed modes, recovery profiles, and preview identity/deadline. Inventory selection preserves output/mode identity and generation, puts the current mode first, and ignores preview-only changes in inventory comparison. The paired status read now retains the display response timing for a conservative host deadline anchor.
- Phase 09: distinct journaled Preview, save-current, saved-profile Restore, preview-baseline Revert, and Keep actions enforce scope, selected target, preview ownership, explicit visible-picture confirmation, and conflict rules. Save-current accepts a single advertised current mode. Keep requires a fresh host deadline anchor; ambiguous Keep results remain unresolved without an automatic Revert. The old-host save-current 404 remains a distinct rejection result for the UI to explain.
- Phase 09: save-current approval now carries the pairing fingerprint, output ID/generation, and current mode observed when its confirmation sheet opens. The dispatcher rejects an approval after output re-enumeration, a current-mode change, or credential refresh before sending `visible:true`; outputs without a valid current mode cannot create the approval object.
- Phase 09: Keep approval now captures the exact pairing, preview ID, output ID/generation, target mode, and host deadline shown when its visible-picture confirmation opens. A changed preview or credential rejects the old approval before dispatch; a missing approval remains a separate block. The host still enforces the preview ID and deadline on the request.
- Phase 09: the protocol decoder now exposes the host's preview identity, semantic modes, and deadline, plus owner-verified profile facts from Keep and save-current replies as bounded typed fields separate from the operation state. It rejects malformed display facts and preview/profile IDs that conflict with the operation identity. The Display screen renders operation and readback cards; their state matrix and live readback behavior remain unverified.
- Phase 09: encrypted state schema v4 introduced a cache of the last valid host-owned recovery profile inventory for the exact active credential (up to eight profiles, including an observed empty list). The pinned status gateway updates it after a successful display read; unchanged inventories avoid another write. After process recreation, one explicit Restore can use the exact cached profile ID with no status read, while the host still validates that target and the journal records an unreachable result without replay. Replacement/Forget clear the cache with the active host.
- Phase 09: blind Restore also ignores a status observation from an older credential when the active credential has its own cached profile inventory. It sends only the exact profile selected from that active cache; a mismatched observation cannot supply preview ownership for Keep or Revert.
- Phases 08–09: current encrypted state schema v5 records pairing time and bearer digest on new journal entries. Known v0–v4 files migrate; older journal entries retain their history but have unknown credential provenance. They cannot own a current preview or be reconciled with an unproven bearer, and unresolved legacy entries conservatively block the same public pairing's mutation lane until reviewed. Proven entries from an older credential do not block a new pairing. The preview projection reconstructs semantic baseline/target modes from a fresh host preview and persisted journal after repository recreation. Migrated unresolved display work remains visible as a review card, with Keep/Revert disabled when it may conflict. Lost Keep replies stay in a checking state, and local deadline expiry means only checking restoration.
- Phase 09: unresolved save-current operations now project a distinct checking card, including after a status read is lost. Migrated save-current records with unproven credential provenance project a review card rather than disappearing while they block conflicting actions.
- Phase 09: encrypted state schema v6 stores an allowlisted rejection code on failed journal entries. The latest display failure projection can distinguish an older host's missing save-current route, stale target, mutation conflict, bridge outage, failed readback, and other pinned host errors after repository reload without parsing host message text. Known v0–v5 files migrate; v5 journal failures retain a null code rather than inventing a reason. A newer display action suppresses an older failure card. The Display screen maps those codes to fixed guidance; the full rendered failure matrix remains pending.
- Phase 09: a delayed failed operation snapshot now also records a fixed failure code. Its exact `readback_not_confirmed` outcome remains distinct after encrypted state reload; other failed outcomes use a generic operation-failed code. The free-form host reason is not used for guidance, and no mutation is replayed during reconciliation.
- Phase 09: a latest-display-operation projection now rebuilds action kind, journal phase, typed failure, and a separate current host observation after repository recreation. It checks exact pairing provenance and freshness before showing preview identity, current-mode match, profile presence, or output re-enumeration. A vanished preview is labeled absent, never confirmed restored; stale, lost, and older-credential reads do not become readback evidence. The Display screen consumes this projection; process-death UI and physical readback evidence remain pending.
- Phases 08–09: a foreground operation reconciler uses a pinned authenticated GET for the saved operation ID, verifies operation ID, request ID, kind, and the selected pairing, then updates the original journal entry. A missing operation ID or pruned 404 never triggers a mutation replay.
- Phases 08–09: the paired foreground session now runs one read-only reconciliation sweep of unresolved, exact-credential journal entries with operation IDs on each visible start. It uses the transport's cancellation signal, stops an in-flight GET when the session stops, and never schedules operation polling or retries a POST in the background. Results return through the session callback; Power, Sunshine, and Display render operation cards and offer an explicit read-only result check.
- Phases 08–09: the operation journal now rechecks the exact active credential inside the transaction that saves a lookup result or pruned 404. A same-host bearer refresh during a delayed GET leaves the old journal entry untouched and reports pairing changed; public host/client IDs alone cannot authorize that late write.
- Phases 08–09: the journal now also checks the route-specific operation kind on the initial mutation reply and on a later operation snapshot. A mismatched power or recovery kind remains unresolved instead of being shown as a successful action.
- Phases 08–09: production application startup now recovers durably `PREPARED` journal entries as `UNKNOWN` before the runtime is exposed. An empty journal or one with no prepared entries does not rewrite encrypted state. This leaves an interrupted mutation available for review or operation lookup without sending it again.
- Phases 08–09: the journal rejects a mutation whose bearer differs from the selected pairing before its prepared entry is committed or its sender is called. If committing a mutation reply fails locally, the exposed operation ID must first match the saved request ID and route-specific kind; a mismatched ID is not offered for reconciliation.
- Phases 08–09: the journal now rechecks the selected credential's unresolved mutation lane inside the same encrypted-state transaction that writes `PREPARED`. Two controls that passed earlier UI preflight cannot both send after a race. A single owned preview can still dispatch its matching Keep or preview-baseline Revert; unrelated and mismatched actions stay blocked. Capacity and duplicate-request rejection keep their existing priority, and historical entries for another credential do not occupy the current lane.
- Phases 08–09: the production mutation sender now sends the exact serialized body committed by the journal after validating it against the request, and prefers the saved host's LAN interface when one is available. A mismatched body is rejected before opening a socket; mutation requests still make one network attempt and are never replayed across interfaces.
- Phase 10: approved pairing credentials stay staged when another host is active. Confirmation checks the exact old pairing during the atomic swap; stale callbacks and failed storage commits retain the old host. Discard journals self-revocation with the staged credential and reports whether host-side removal was confirmed. A bounded diagnostics serializer exports only named status and journal facts, excluding stored request bodies, secrets, IDs, raw exceptions, and host error text.
- Phase 10: a delayed self-revocation reply clears an active credential only if the endpoint, pin, bearer token, and pairing timestamp still match the exact credential used for that request. Re-pairing the same host and client IDs during a revoke cannot erase the newer credential.
- Phase 10: the ID-only local Forget entry point was removed. Replacement, Forget, repair, status, control, and operation lookup now compare the saved bearer as well as host/client/endpoint/pin and pairing time, so a credential refresh with the same public identity cannot satisfy a stale action.
- Phase 10: the Android runtime now exposes a document writer for an explicit `ACTION_CREATE_DOCUMENT` result. It accepts only a content URI, generates the bounded sanitized diagnostic export before opening the destination, writes no decrypted store file locally, and returns fixed result codes rather than provider exceptions or raw error text. Connection Details now launches the system document picker and writes only to its returned content URI; picker interaction still needs device evidence.
- Phase 10: diagnostic export format v2 adds a nullable allowlisted journal failure code. A known display/control failure can be diagnosed without including the host's free-form reason, request/operation IDs, credentials, or raw request body. The 16 KiB export bound remains enforced; the rendered picker action is wired but has not been exercised end to end.
- Phase 06 prerequisite: the user accepted the documented unscored Compose/Roborazzi dependency set on 2026-09-28. The app now applies the Compose compiler plugin, locks the resolved AndroidX/Roborazzi/Robolectric graph, and records SHA-256 verification metadata. A launchable Compose Activity, theme, component primitives, and `SavedStateHandle` navigation are present. Most Phase 06 fixture and accessibility gates remain open.
- Phase 08 UI in progress: the paired Activity owns one foreground status/operation/Wake session. Power presents an exact-target confirmation captured when the dialog opens; its ViewModel sends the journaled request off the main thread. Wake sends one explicit packet and shows packet, authenticated response, and Steam readiness separately. Sunshine recovery uses the shared availability gate and journaled dispatcher. These screens compile; live control acceptance and physical Wake packet capture are still pending.
- Phase 09 UI in progress: the Display screen keeps output/mode selection stable across preview-only status changes, orders the current mode first, shows the host preview/recovery card and a separate latest-operation/current-observation card, and wires Preview, Keep, Revert, Restore, and save-current through distinct journaled actions. Keep and save-current capture exact-target confirmation facts when their dialogs open. This is not yet a completed fixture matrix or physical controlled-failure journey.
- Phase 10 UI in progress: Connection Details renders the staged replacement and discard decisions, local Forget versus host revoke, a bounded operation journal, and a sanitized export action. Pairing a second host returns to an onboarding flow while retaining the original credential until the atomic swap. The Activity reopens encrypted state and the paired session after a credential change. The display-order destination remains gated by the shared plan.
- Phase 07 UI prerequisite in progress: launchable onboarding, discovery, manual address, candidate details, comparison code, pairing approval, and a Camera2 scanner/paste route are wired to the existing coordinator and Android permission flows. Live host pairing, QR camera behavior, and complete fixture rendering have not been exercised.
- The paired overview now offers an explicit status refresh. It uses the app's user-initiated local-network permission flow before requesting the authenticated read, so an existing pairing can recover from an ungranted API 37 permission without starting a new pairing.
